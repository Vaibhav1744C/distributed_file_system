REAL DFS

The coordinator runs as a Win32 process. Each storage node is a separate process launched by ProcessManager::launchStorageNode() via CreateProcessW() in src/process/process_manager.cpp. Within the coordinator, four std::thread instances run concurrently — HTTP server, RPC server, worker scheduling loop, and health monitor. Process state (PID, memory, handle) is tracked in the ProcessState struct and monitored using GetProcessMemoryInfo() via PSAPI. Clicking "Simulate Crash" above calls TerminateProcess(); the health monitor detects the missing heartbeat in under 5 seconds and marks the node OFFLINE in SQLite.

The Windows OS schedules the coordinator and storage-node processes as standard Win32 processes — CPU time is allocated by the OS kernel, not the DFS. Internally, the DFS has its own application-level RequestScheduler (src/scheduler/request_scheduler.cpp) that queues file I/O requests (upload, download, delete) using FCFS, Priority with aging (+1 boost per 200ms waited), or Round Robin with a 50ms quantum. This request scheduler controls the order in which file operations are serviced — it is distinct from OS CPU burst scheduling shown in the Gantt chart above. When two clients upload simultaneously, both requests enter the queue and are dequeued by Coordinator::workerSchedulingLoop() according to the selected algorithm.

Concept: Reader-Writer Locks & Deadlock Prevention

Reader-Writer Locks allow multiple concurrent SHARED_READ holders but require exclusive access for EXCLUSIVE_WRITE.

Havender Lock Ordering: Locks are always acquired in lexicographic sorted order, eliminating Circular Wait without rollback.

Wait-For Graph: Edge A→B means A waits for a resource held by B. A cycle proves deadlock. DFS-based cycle detection runs on every lock request.

REAL DFS

Every file upload acquires an EXCLUSIVE_WRITE lock on the target path; every download acquires a SHARED_READ lock. Multiple readers can hold the lock simultaneously, but a writer waits until all readers release. This is implemented in LockManager (src/sync/lock_manager.cpp) using std::mutex and std::condition_variable. Rename operations acquire locks on both paths in alphabetical order — Havender's ordering — which eliminates circular wait. Lock acquisition has a 3–5 second timeout; on expiry the operation fails and the WAL transaction is aborted. detectDeadlockCycle() builds a Wait-For Graph after every acquisition as a safety net. The "Active Locks" table above reflects the live state from /api/locks.

Four Necessary Conditions: Mutual Exclusion, Hold and Wait, No Preemption, Circular Wait. Eliminating any one prevents deadlock.

REAL DFS

Our DFS prevents deadlock using Havender's lock ordering in LockManager::acquireMultipleLocks() — locks are always acquired in lexicographic order, eliminating circular wait before it can form. If a lock still cannot be acquired within 5 seconds, the call returns false and the transaction is aborted (recovery without deadlock). detectDeadlockCycle() additionally builds a Wait-For Graph and runs DFS cycle detection as a detection layer. The RAG playground above lets you construct equivalent scenarios manually — for example, two rename operations crossing the same two paths — to see how the circular-wait condition forms and how ordering prevents it.

Our DFS does not implement Banker's Algorithm. Banker's requires each client to declare maximum resource needs in advance, which is impractical for a dynamic file system with unpredictable concurrent clients. The DFS achieves the same safety goals through lock ordering (prevention) and WFG cycle detection (detection) in src/sync/lock_manager.cpp. The matrix simulation above is an educational demonstration of the safety algorithm theory. It is directly relevant to OS resource management and provides the conceptual foundation for understanding why safe-state analysis matters in systems with multiple shared resources.

REAL DFS

During upload, the coordinator splits file data into 64KB MemoryChunk objects and pushes them into a 16-slot BoundedBuffer (include/buffer/bounded_buffer.h). If all 16 slots are full, push() blocks the upload thread via cv_not_full_.wait_for() until the TCP sender frees a slot — this is backpressure. On download, the reassembled file is stored in LruFileCache (include/cache/lru_cache.h) — a 64-item doubly-linked-list + hashmap structure. A cache hit returns data without a TCP round-trip to storage nodes. The OS manages virtual memory pages for all of this via Windows VirtualAlloc transparently. The DFS does not implement paging, page tables, or partition allocation algorithms itself.

REAL DFS

A file in our DFS is stored as a sequence of 64KB chunks, each with a unique ID ({file_id}_chk_{index}) and a SHA-256 hash. The MetadataManager (src/metadata/metadata_manager.cpp) stores the complete record in SQLite: path, owner, Unix-style permissions (e.g. 0755), version, size, SHA-256, and the full chunk-to-node mapping. On download, the coordinator fetches each chunk from a healthy replica node and verifies its hash before assembling the response. Uploading report.pdf (10MB) creates 160 chunks, each replicated to 2 nodes — so 320 total chunk writes across the cluster. If Node 1 goes offline, its chunks are transparently read from Node 2.

I/O Buffer & Cache

Bounded producer-consumer buffer • LRU cache • Real-time metrics
Bounded Ring Buffer (16 slots)

16-slot circular FIFO holding 64KB file chunks. Backpressure: when full, the producer blocks on a condition variable until a consumer drains a slot. Linux equivalent: pipe() with kernel buffer limits.

LRU File Cache
LRU Chain (MRU to LRU):

On HIT data is returned from memory. On MISS data is fetched from nodes and inserted at MRU position. On write/delete the entry is invalidated to maintain cache coherence. Linux equivalent: page cache in VFS layer.

REAL DFS

The bounded buffer is a 16-slot ring of MemoryChunk objects (BoundedBuffer<MemoryChunk>). During upload, the upload thread is the producer; a background TCP sender is the consumer. When all 16 slots are occupied, the producer blocks on cv_not_full_.wait_for(). When a slot frees, it is notified and continues. Uploading a 1MB file produces exactly 16 chunks — the buffer fills completely, so chunk 17 would block until chunk 0 is sent and its slot freed. The LRU cache sits above this: a cache hit on download skips the buffer entirely and returns data from memory. The ring and cache statistics above are fetched live from /api/buffer and /api/cache.

Write-Ahead Log & Crash Recovery

ACID transactions • LSN journal • Automatic rollback on crash
WAL Journal
LSNTX IDOperationFile PathStateTimestamp
WAL Lifecycle

Write-Ahead Logging: Before any data modification the operation is appended to a durable log with a Log Sequence Number (LSN). States: PENDING then COMMITTED or ROLLED_BACK.

Crash Recovery: On coordinator startup the WAL manager scans for PENDING entries and rolls them back, ensuring atomicity. Linux equivalent: journald in ext4/XFS filesystems.

REAL DFS

Every file operation is wrapped in a WAL transaction. WalManager::beginTransaction() writes a PENDING entry to SQLite with an LSN before any data moves. After all chunks are stored on nodes, commitTransaction() marks it COMMITTED. If the coordinator crashes between those two steps — after chunk storage but before the commit — runCrashRecovery() finds the PENDING entry on restart and calls abortTransaction(), removing partial metadata. The upload appears as if it never happened. This is the same principle used by ext4 journal and NTFS transaction logs. All entries shown above are live from /api/recovery.

Our DFS is Windows-native and uses Win32 API calls, not Linux system calls. The concepts map directly: CreateProcessW ≡ fork+exec, CreateFile/ReadFile/WriteFile ≡ open/read/write, WSASend/WSARecv ≡ write/read on a socket fd, VirtualAlloc ≡ mmap. The animation above shows the Linux ring 3→ring 0 privilege transition and syscall dispatch table — this is the architectural model that Win32 API calls follow through the Windows NTAPI layer. When the coordinator calls send() to transfer a chunk to a storage node, it crosses from user space into the Windows kernel exactly as shown, just via the Windows syscall mechanism rather than Linux int 0x80.

Security & Audit Log

REAL DFS

SecurityManager::recordAudit() (src/security/security_manager.cpp) is called at the end of every significant operation — upload, download, delete, rename, node kill, lock timeout, permission denial. Entries are written to SQLite via MetadataManager::addAuditLog() and served by /api/audit. Path traversal attempts (e.g. /docs/../etc/passwd) are caught by sanitizePath() and logged as failed with action UPLOAD and success=false — they appear in the table above with a red DENIED badge. Every entry includes user, action, target path, client IP, timestamp, and a human-readable detail string.
